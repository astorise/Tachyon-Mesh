- [x] **Task 4: Tensor-parallel execution**
  - Added `core-host/src/ai_inference/tensor_parallel_llama.rs`: a from-scratch, Megatron-style tensor-parallel Llama forward pass (`TensorParallelLlama`, `TensorParallelBlock`, `TensorParallelMlp`, `ReplicatedAttention`, `TensorParallelCache`). Reimplemented rather than patched onto `candle_transformers::models::llama::Llama` because that crate's `Block`/`Mlp`/`CausalSelfAttention`/`Cache` internals are private — confirmed by reading the upstream source (`candle-transformers-0.10.2/src/models/llama.rs`); only `Llama`, `Config`, `LlamaConfig`, and `Cache::new`/`use_kv_cache` are `pub`.
  - **Scope, per `design.md` §2**: sharding is MLP-only. `gate_proj`/`up_proj` are column-parallel-sharded (`ColumnParallelLinear`) and `down_proj` is row-parallel-sharded (`RowParallelLinear`) across the supplied `devices: &[Device]`, reusing the existing tested primitives in `parallel.rs`. The all-reduce after the down-projection is the existing `RowParallelLinear::forward`'s partial-sum reduction (CPU-staged summation today; becomes an NCCL all-reduce once real multi-GPU/NCCL wiring lands under `gpu-accelerated-inference-execution`). Attention, embeddings, and the LM head are replicated on a single primary device (`devices[0]`) — not sharded — since `design.md` only describes MLP up/gate/down sharding.
  - Fixed a latent rank-mismatch bug surfaced by this work: `ColumnParallelLinear`/`RowParallelLinear::forward` only worked for 2-D `[batch, features]` inputs (`candle_core::Tensor::matmul` requires equal rank on both operands, with no implicit broadcasting). `TensorParallelMlp::forward` now flattens the `[batch, seq, hidden]` activation to 2-D before calling these primitives and reshapes the result back, so real (3-D) transformer activations work without changing `parallel.rs`'s existing tested contract.
  - **Verification**: two new tests load the same tiny real Llama checkpoint (via the existing `write_tachyon_tiny_fixture` helper) into both the upstream dense `Llama` (1 device) and the new `TensorParallelLlama` (2 simulated devices, both `Device::Cpu` since this build has no live CUDA backend — see Task 2's caveat), and assert logits match within `1e-3`: once for a fresh multi-token prompt, and once for a second decode step continuing from a populated KV cache. Both pass; the full `tensor_parallel_llama::` and `parallel::` suites (12 tests total) pass with no regressions.
  - **Caveat — not yet a live execution path**: `candle_llm_runtime.rs`'s `try_load(alias, path, requested_device: &str)` hard-rejects any `requested_device != "cpu"` today, and `LoadedModel` has no tensor-parallel variant. There is currently no caller anywhere in `core-host` that takes a deployment's `hardware_strategy` (`distribution_mode: tensor_parallelism`, `device_ids`) and threads it into model loading to actually select `TensorParallelLlama` over the dense `Llama` at runtime. This task delivers the tensor-parallel engine itself, proven numerically equivalent to the dense reference; wiring it into `CandleLlmRuntime`'s load/dispatch path so a real deployment can select it is left for a follow-up once real multi-device hardware enumeration (Task 2's caveat) and CUDA/NCCL execution (`gpu-accelerated-inference-execution`) land — gating it behind `multi_gpu: true` + `distribution_mode: tensor_parallelism` as specified will only have observable effect once that caller exists. The pre-existing single-GPU/CPU path (`LoadedModel::Safetensors`/`Gguf` via `try_load`) is completely untouched by this change, so it remains byte-for-byte unaffected.

- [x] **Task 5: Pipeline-parallel execution**
  - **Per-stage executor — scope correction**: the task as written says to reuse `ai-layer-wise-inference`'s per-layer streaming primitive (`ai_inference::PrefillBatch::run`/`LayerWiseMappedModel`). Reading that primitive shows it implements a placeholder forward pass — its own doc comment says "mock matmul... Real implementation: call into a Candle transformer block here" — so it could not be the basis of a numerically-verified pipeline engine. Added `core-host/src/ai_inference/pipeline_parallel_llama.rs` instead, which reuses Task 4's real, already-tested `TensorParallelBlock` (loaded with a single-device slice, which degenerates its MLP sharding to the dense case) as the per-stage unit of work. A `PipelineStage` owns a contiguous `[start, end]` layer range plus the token embedding (stage 0 only) / final norm + LM head (last stage only), and implements `parallel::PipelineStageExecutor`; `PipelineParallelLlama` composes stages and drives a prefill forward across them.
  - **Cross-node transport — design.md correction**: `design.md` describes reusing "the existing mesh transport (gRPC/HTTP2 capability `grpc-http2`)". Investigation found this is inaccurate: `grpc-http2` (`openspec/specs/grpc-http2/spec.md`) is the FaaS guest-request HTTP/gRPC router, unrelated to node-to-node communication — there was no existing mesh transport to reuse, and `core-host/src/mesh/` only contains geo-migration routing logic with no network send/recv. Added `TcpStageTransport` to `parallel.rs`: a real point-to-point transport over a plain TCP socket (length-prefixed `[ndims][dims][f32 data]` frames), implementing the existing `StageTransport` trait — `send()` connects to the peer hosting the next stage, pushes the activation, and blocks for the tensor the peer computed; `serve_one()` is the peer-side counterpart. Verified with a real OS-socket round trip in `tcp_stage_transport_round_trips_an_activation_over_a_real_socket` (`parallel.rs`) and end-to-end against the dense reference in `pipeline_parallel_llama_hands_off_activations_over_a_real_tcp_socket`. Pointing `addr` at a remote host requires no further code changes; gRPC/HTTP2 framing can replace the wire format later without changing `StageTransport`'s contract.
  - **Bounded micro-batch scheduling**: added `run_pipeline_microbatched` to `parallel.rs`, which actually wires the pre-existing (previously untested-in-context) `PipelineDepthGate` into a GPipe-style schedule: at each tick every admitted, unfinished microbatch advances by one stage, and new microbatches are admitted as soon as the gate has spare depth. Verified against the single-batch `run_pipeline` reference in `microbatched_pipeline_matches_running_each_microbatch_through_run_pipeline_alone`. This reference scheduler still executes every tick sequentially in-process, so it proves the admission/ordering logic correctly but does not yet produce real wall-clock stage overlap — that needs one execution thread/process per stage, left as follow-up (the same per-node split `TcpStageTransport` is built for).
  - **Verification**: two new tests in `pipeline_parallel_llama.rs` load the same tiny real Llama checkpoint into both the dense reference `Llama` and a 2-stage `PipelineParallelLlama` and assert logits match within `1e-3`: once with an in-process transport, once with stage 0→1 handed off over a real TCP socket (a background thread serves stage 1). Plus 2 new tests in `parallel.rs` (`run_pipeline_microbatched`, `TcpStageTransport`). All pass; full `ai_inference::` suite (84 tests) has no regressions.
  - **Caveat — same class as Task 4's**: this delivers the pipeline-parallel engine, transport, and scheduler, proven correct; no live caller in `candle_llm_runtime.rs` yet threads a `pipeline_parallelism` deployment's `stage_layer_ranges`/`device_ids` into model loading to select `PipelineParallelLlama` over the dense path. Per-stage execution here is also prefill-only (KV-cache-free, `index_pos` always 0) — carrying a per-stage KV cache across decode calls is part of the dispatch-path wiring, not this task's verified surface.

- [x] **Task 6: Expert-parallel (MoE) execution**
  - **Checkpoint detection**: added `detect_expert_count(tensor_names, layer_idx)` in `core-host/src/ai_inference/parallel.rs`, a pure function that scans tensor-name strings for the `<prefix>.layers.<layer_idx>.*.experts.<id>.*` naming convention (Mixtral/Qwen-MoE style — confirmed by reading `candle-transformers-0.10.2/src/models/mixtral.rs`'s `SparseMoeBlock`/`BlockSparseTop2MLP` weight-loading paths, which are private to that crate and a wholly separate architecture from Llama, the same "private internals force reimplementation" situation as Task 4) and returns the highest expert id found, or `None` for a dense layer. `None` is the signal callers use to fall back to the existing dense path unchanged.
  - **Gate-then-route dispatch**: added `ExpertMlp` (one expert's Mixtral-style SwiGLU MLP — `w2(silu(w1(x)) * w3(x))` — resident on whichever device `ExpertPlacementPlan` (pre-existing, already-tested in this module) assigns it to) and `ExpertParallelMlp` (a replicated top-1 gate plus `Vec<ExpertMlp>`). `ExpertParallelMlp::forward` computes gate logits once on the primary device, selects each token's top-1 expert, groups token indices **by expert id** (not just by device, so two experts sharing a device still only ever see their own tokens), gathers only the assigned rows via `index_select`, moves that batch to the expert's device, runs only that expert's MLP over only those rows, moves the result back, and scatters into the output at the original token positions — so no expert ever processes a token it wasn't routed to, and no dense replication of expert weights across devices occurs.
  - **Verification**: `expert_parallel_mlp_matches_per_token_dense_dispatch_reference` builds a 4-expert/2-device plan and asserts the batched, multi-device, grouped-by-expert output matches a reference that routes and computes each token individually (single-row matmuls straight from the same weights) within `1e-4`, proving the grouped dispatch is numerically identical to literal sparse per-token routing. Plus two `detect_expert_count` unit tests (a fabricated MoE layer's tensor names → correct expert count; a fabricated dense layer's tensor names → `None`). All 3 new tests plus the existing 12 in `parallel::` pass (15 total); full `ai_inference::` suite is 87 tests, 0 regressions (was 84 after Task 5).
  - **Caveat — same class as Tasks 4 and 5's**: `candle_llm_runtime.rs` has no MoE/Mixtral checkpoint loader at all today — there is no live caller that detects an MoE checkpoint via `detect_expert_count` and selects `ExpertParallelMlp` over the dense `TensorParallelMlp`/`TensorParallelBlock` path. This means "fall back to the existing dense path for non-MoE checkpoints" is trivially and safely true right now: nothing in the runtime currently attempts to load an MoE checkpoint, so the pre-existing dense path is the only one ever exercised in production, unaffected by this change. Wiring a real MoE loader (parsing `num_local_experts`/`num_experts_per_tok` from config, calling `detect_expert_count` per layer, building `ExpertPlacementPlan` from the deployment's `hardware_strategy`, and substituting `ExpertParallelMlp` into the per-layer forward pass) is left for the same follow-up as Tasks 4-5's dispatch-path wiring, gated on real multi-device hardware (Task 2's caveat) and CUDA/NCCL execution (`gpu-accelerated-inference-execution`).
