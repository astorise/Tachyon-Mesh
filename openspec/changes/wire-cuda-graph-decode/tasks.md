- [x] 1.2 Tag a new fork release once that PR merges and its own tests pass: `tachyon-v0.11.0-4` (same tag as `wire-flashinfer-decode-attention`'s prerequisite — both landed together).
- [x] 1.3 Bump `core-host/Cargo.toml`'s pinned `astorise/candle` tag to the new release (shared with `wire-flashinfer-decode-attention`).
- [x] 1.4 **Second, unanticipated fork dependency** (design.md Decision 5): `PagedKvCache::write_new_kv` computed its scatter destinations via a blocking device-to-host `Tensor::to_vec2` readback of `block_table` — not capturable at all, independent of the rotary-embedding problem 1.1 solves. Filed as [astorise/candle#15](https://github.com/astorise/candle/issues/15); landed via [astorise/candle#16](https://github.com/astorise/candle/pull/16) as `Cache::set_paged_kv_decode_slot`/`write_new_kv`'s new `decode_slot: Option<&Tensor>` parameter — when attached, `write_new_kv` scatters directly against a caller-supplied `(b_sz,)` flat-index tensor instead of re-deriving indices from a block-table readback. Tagged `tachyon-v0.11.0-6`; pinned tag bumped again.
- [ ] 1.5 **Third, unanticipated fork dependency, still open** (design.md's "Known limitation, still open" section): `CudaGraph::capture` only paused `candle-core`'s internal event-tracking bookkeeping for the duration of the capture call itself, not the resulting graph's whole lifetime — a second, independent `capture()` on the same device later fails with `CUDA_ERROR_INVALID_VALUE` on an unrelated allocation. Filed as [astorise/candle#17](https://github.com/astorise/candle/issues/17). **First fix attempt** (tagged `tachyon-v0.11.0-7`: `EventTrackingGuard` held for the `CudaGraph` struct's entire lifetime) matched the hypothesis exactly and passed the fork's own new regression test, but re-testing our actual scenario (a captured multi-layer `Llama::forward`, not the fork test's single elementwise op) on real hardware showed the identical failure, unchanged. Reported back and reopened the issue with this finding. Pinned tag bumped to `tachyon-v0.11.0-7` anyway (no regressions from it, and it's needed groundwork regardless of whether it alone resolves this), but the multi-request limitation itself is **still open**.

## 2. Runtime wiring

- [x] 2.1 In `try_load_with_topology`, replace the unconditional `cuda_graph_decode` rejection with a gate requiring Llama + CUDA + `paged_attention: true` (design.md Decision 2); reject with a typed error naming the `paged_attention` dependency when it's missing, and keep the existing rejection for every other combination. **Two bugs caught by an automated (Codex) review and fixed** before capture/replay existed: (1) `single_device_cuda_supported` (shared with `paged_attention`/`flashinfer_attention`) didn't check `distribution_mode == Single` — fixed by adding that check to `single_device_cuda_supported` itself. (2) The gate used to fall through with no rejection at all once every prerequisite was met, silently running the uncaptured loop — fixed with an unconditional rejection at the time, since capture/replay didn't exist yet. That unconditional rejection is now removed: with 1.4 landed and 2.2/2.3 implemented below, a fully-satisfied request now loads and runs a real captured decode instead of being rejected.
- [x] 2.2 `CudaGraphDecodeSession` (new struct in `candle_llm_runtime.rs`, `#[cfg(feature = "candle-cuda")]`) pre-allocates `token_buf` `(1,1)`, `position_buf`/`decode_slot_buf` `(1,)`, `block_table_buf` `(1, min_blocks)` (full width from the first decode step — the pool is already capped at `min_blocks`, so no recapture is ever needed), `seqlens_buf` `(2,)`, and `logits_buf` `(1, vocab_size)`, once per request. `Self::write_step` updates all of them via `Tensor::slice_set` only — device-to-device, no host readback, computing the flat scatter index itself from the host-side `SequenceBlockTable` (the same formula `write_new_kv`'s old host path used) instead of asking the fork to re-derive it.
  - **Real bug caught by `cuda-quality` on actual GPU hardware**: the first real-hardware run got through compile, clippy, and every earlier CUDA proof (NCCL, single-device, paged-attention, the gate test), then failed inside `single_device_llama_cuda_graph_decode_generates_a_real_captured_decode_on_cuda` with `unexpected rank, expected: 3, got: 2 ([1, 1, 4])`. `logits_buf` had been allocated as `(1, 1, vocab_size)` on the (wrong) assumption that `Llama::forward` returns `(batch, seq_len, vocab_size)`; it actually returns `(batch, vocab_size)` — rank 2, no separate seq_len dimension — confirmed by `decode_loop_from_logits`'s own `logits.squeeze(0)`, which removes exactly one (batch) dimension before sampling. Fixed by allocating `logits_buf` as `(1, vocab_size)`. This is exactly the class of mistake the whole `candle-cuda`-gated implementation was at risk of, per 3.2's note below — a shape assumption that compiled and clippy'd cleanly (shape isn't a Rust type) but was simply wrong, only observable by actually running it.
- [x] 2.3 `CudaGraphDecodeSession::establish` attaches `position_buf`/`decode_slot_buf`/the paged-KV tensors to every layer once, runs one uncaptured warm-up forward pass under `CudaDevice::enable_cuda_graph_htod_cache`, captures a second logical call via `CudaGraph::capture`, then replays once for the first decode step's real logits. `replay_step` updates the buffers for each subsequent step and calls `graph.replay()`. `SingleDeviceBackend::decode`'s Llama arm gained a `Some(paged) if *cuda_graph_decode` match arm (before the plain `Some(paged)` arm) that routes prefill (`seq_len != 1`) through the existing uncaptured `paged_llama_forward` unconditionally, and decode steps (`seq_len == 1`) through `establish`/`replay_step`, holding an `Option<CudaGraphDecodeSession>` across the closure's calls (`None` until the first decode step). `model.forward`'s `index_pos` argument is passed as a fixed `0` for every warm-up/capture/replay call — with both `set_decode_position` and `set_paged_kv_decode_slot` attached, the paged decode path never reads it, confirmed by re-reading every `index_pos` use site in the fork's `CausalSelfAttention`/`Llama::forward` chain.
- [x] 2.4 LoRA adapters and speculative decoding: unaffected, same reasoning as `wire-flashinfer-decode-attention`'s equivalent audit — LoRA reloads its own model per request via a separate code path that never touches `cuda_graph_decode`, and speculative decoding already falls back to plain generation whenever either side is paged-attention-enabled (`is_paged_attention_enabled()`), which every `cuda_graph_decode` deployment is by construction. Prefix caching is already independent of the paged branch entirely (only used by the non-paged `None` arm).
- [ ] 2.5 **Still open** (see 1.5 and design.md's "Known limitation, still open" section): a *second* request against an already-loaded `cuda_graph_decode` model fails at `Cache::new(...)` with `CUDA_ERROR_INVALID_VALUE`. The fork's first fix attempt did not resolve our real-world scenario (confirmed on real hardware, iteration 5 below). No Tachyon-Mesh-side mitigation (e.g. falling back to the uncaptured path after a model's first `cuda_graph_decode` request) has been implemented — scoping that remains an open decision. **`cuda_graph_decode` is still not safe to enable for any model expected to serve more than one request.**

## 3. Tests

- [x] 3.1 `cuda_graph_decode_strategy_is_rejected_until_gpu_decode_is_wired` (requests `cpu`) still passes — rejection still fires for a non-CUDA device request. `cuda_graph_decode_strategy_is_rejected_without_paged_attention` (`#[cfg(feature = "candle-cuda")]`) still passes — rejection still fires without `paged_attention`. `paged_attention_strategy_is_rejected_for_a_non_single_distribution_mode`/`flashinfer_attention_strategy_is_rejected_for_a_non_single_distribution_mode` (CPU-testable) still pass — the shared `distribution_mode` gate fix. The interim `cuda_graph_decode_strategy_is_rejected_even_with_paged_attention_until_capture_is_wired` test (asserting rejection even with every prerequisite met) is **removed** — that combination is now expected to succeed, replaced by 3.2 below.
- [x] 3.2 Added `single_device_llama_cuda_graph_decode_generates_a_real_captured_decode_on_cuda` (`#[cfg(feature = "candle-cuda")]`): loads the dedicated paged-attention fixture with both `paged_attention: true` and `cuda_graph_decode: true`, asserts non-empty output, asserts it **matches** a separate paged-attention-only (no `cuda_graph_decode`) runtime's greedy output for the same prompt. Written and reasoned through as carefully as possible before ever reaching real hardware — this dev machine's local CUDA toolchain doesn't compile (see `project_hardware_strategy_accelerations` memory), so `CudaGraphDecodeSession` could only be reviewed by hand before each `cuda-quality` run.
  - **Iteration 1**: caught the `logits_buf` rank bug documented in 2.2 (compile and clippy were clean — a wrong shape isn't a Rust type error — only the actual GPU run surfaced it). Fixed.
  - **Iteration 2**: with that fixed, the test's core assertions (non-empty output, output matches the non-captured paged-attention path exactly) **passed** — confirming the capture/replay logic itself, including the position/decode-slot device-tensor seams, produces numerically correct output over multiple decode steps within one request. A third assertion at the time (a *second* `generate()` call on the same loaded runtime) failed with `CUDA_ERROR_INVALID_VALUE` from an unrelated `Cache::new(...)` call. Added a defensive `Drop`-based synchronize — did not help.
  - **Iteration 3**: identical failure, same location, with the synchronize fix in place — ruling out a timing explanation. Isolated further (removed a second model load that had been interleaved between the two `captured_runtime` calls) — same failure. Filed [astorise/candle#17](https://github.com/astorise/candle/issues/17) with the event-tracking hypothesis; simplified the test to assert only a single request per loaded runtime (the scope proven to work) so the core capability could ship independently of the open multi-request question. **Confirmed green on `cuda-quality`** in this reduced form.
  - **Iteration 4**: astorise/candle#17's first fix landed (see 1.5) — restored the second-request assertion, bumped to `tachyon-v0.11.0-7`.
  - **Iteration 5**: re-ran on real hardware — **identical failure, same location, unchanged**, despite the fix's mechanism matching our hypothesis exactly and passing the fork's own new regression test. Confirmed the CI run genuinely compiled against the fix commit. Reported back on astorise/candle#17 (reopened) with the likely explanation (our capture region — a full multi-layer `Llama::forward` — is far more complex than the fork's single-op regression test; possibly a memory-pool-level issue the per-tensor event-tracking fix doesn't cover). **Removed the second-request assertion again** — back to the proven single-request scope while the fork investigates further.
- [x] 3.3 Regression on the default (non-`candle-cuda`) build: `cargo test -p core-host --features ai-inference ai_inference::` (188/188, 0 regressions), `cargo clippy --workspace --all-targets --features core-host/ai-inference -- -D warnings -D clippy::unwrap_used` (clean), `RUSTFLAGS="-D dead_code" cargo check -p core-host --features ai-inference` (clean — `CudaGraphDecodeSession` is entirely absent from this build, not merely unused), `cargo fmt --all -- --check` (clean).
