# Specification: Automated Canary Deployments

## 1. Fractional Routing Implementation
The router currently directs traffic to the active component instance. We need a routing layer capable of weighted distribution.
* **State Addition:** The routing table must maintain a tuple of `(current_version, next_version, current_weight_percentage)` during a rollout.
* **Execution:** For incoming requests, generate a random number `n` between 1 and 100. If `n <= current_weight_percentage`, route to `next_version`. Otherwise, route to `current_version`.

## 2. Telemetry Feedback Loop (`canary_evaluator`)
The background worker orchestrating the rollout requires read access to the `TelemetrySnapshot`.
* **State Machine:** The evaluator state machine transitions from `Init` -> `Stepping` -> `Evaluating` -> `Promoted` or `RolledBack`.
* **Threshold Calculation:** During the `Evaluating` phase, compute the error rate specifically for `next_version` using: `(5xx_responses + wasm_traps) / total_invocations`.
* **Atomic Rollback:** If the threshold is breached, the routing state must atomically revert the weight to `0` and emit a critical system event (visible in the Shadow Diffs/Events log).

## 3. UI Integration (`TachyonWorkloadsPanel`)
* Ensure the JSON payload generated by the form correctly matches the new WIT schema.
* Display the rollout state. Example: `Status: Deploying (Canary) - 40% traffic shifted`.
* Add an explicit "Abort Rollout" button next to the progress bar that sends an override command to the core host, instantly resetting the traffic to the previous version.
