# Proposal: Real NCCL All-Reduce, NVML VRAM Telemetry, and GPU-Proof CI for Tensor-Parallel Inference

## Why
`2026-06-19-distributed-model-parallel-inference` (merged via PR #187) delivered the tensor/pipeline/expert-parallel execution engines and `9e72d1f` (PR #204, merged on `main`) wired them into runtime dispatch and activated the real `candle-cuda` build. Independently re-verified against `origin/main` and the `cuda-quality` CI job's actual run history (run #961, job 82767837303, on self-hosted runner `arc-gpu-runners-bjc7r-runner-l6s99`):

- A real GPU was present and detected (`nvidia-smi` reported an `NVIDIA GeForce RTX 3060`), `nvcc` was found, and `cargo clippy -p core-host --features candle-cuda --all-targets -- -D warnings -D clippy::unwrap_used` finished cleanly. **The CUDA build activation is real and lint-clean on real GPU hardware**, not merely configured.
- However, three gaps remain, all confirmed by direct code inspection of `core-host/src/ai_inference/parallel.rs` on `origin/main`:
  1. **No NCCL collective exists anywhere in the tree** (`grep -i nccl` across `parallel.rs` returns zero implementation hits — only doc comments describing what an NCCL all-reduce "would" sum, and a test name). `RowParallelLinear::forward`'s synchronization is a host-staged manual sum across `Tensor::to_device`-moved values: every shard's partial output is copied to one "reduce device" and added in a loop. This works for correctness but does not exercise any real multi-GPU collective communication path, and would not scale to a multi-node tensor-parallel group.
  2. **`discover_cluster_topology` hardcodes `free_vram_bytes: 0`** for every device it enumerates (including real CUDA ordinals found via `Device::cuda_if_available` under the `candle-cuda` feature). This makes `validate_parallel_topology`'s `VramPerShardExceeded` check permanently inert in production — a deployment that would not fit in VRAM is never rejected on that basis, because every device always reports 0 bytes free.
  3. **A verified, shipped comment bug**: the inline comment above `discover_cluster_topology`'s CUDA enumeration loop reads *"With the candle CUDA backend compiled in (`candle-cuda`, pulled by `nvfp4-cuda`)..."*, but `core-host/Cargo.toml` defines `nvfp4-cuda = ["ai-inference"]` and `candle-cuda = ["ai-inference", "candle-core/cuda", ...]` as separate, sibling features — `nvfp4-cuda` does **not** enable `candle-cuda`. A reader or operator following this comment would wrongly conclude that loading an NVFP4 checkpoint is sufficient to get multi-GPU enumeration; it is not.

None of these three gaps are caught by the existing `cuda-quality` CI job, which only proves the code *compiles and lints* against the real CUDA toolchain — it does not run any test that exercises multi-GPU tensor-parallel execution or asserts a numeric result on real hardware.

## What Changes
1. **Real NCCL all-reduce**: replace `RowParallelLinear`'s host-staged manual-sum reduction with a real NCCL `AllReduce` collective when the `candle-cuda` feature is active and more than one CUDA device participates in a tensor-parallel shard group, using `candle_core`'s/`cudarc`'s NCCL bindings (or a thin wrapper over `nccl-sys`/`cudarc::nccl` if `candle_core` does not expose one directly). The existing CPU-staged sum remains the fallback for non-CUDA builds and for `Device::Cpu` shard groups, so the single-device and CPU-multi-device test paths are unaffected.
2. **NVML-backed VRAM telemetry**: bind NVML (via `nvml-wrapper` or equivalent) behind the `candle-cuda` feature so `discover_cluster_topology` reports each CUDA device's real free VRAM (`nvmlDeviceGetMemoryInfo`) instead of a hardcoded `0`, making `VramPerShardExceeded` validation actually enforceable on real hardware. CPU-only builds keep reporting `0` (unknown), preserving existing behavior where NVML is unavailable.
3. **Fix the verified comment bug**: correct the `discover_cluster_topology` comment to accurately state that `candle-cuda` is a separate, sibling Cargo feature to `nvfp4-cuda`, not implied or pulled in by it.
4. **GPU-proof CI**: extend the `cuda-quality` job (or add a sibling job on the same `arc-gpu-runners` self-hosted runner) to actually *run* a multi-GPU (or, where only one physical GPU is available, an NCCL single-process multi-rank) tensor-parallel all-reduce test and assert its numeric output matches the existing CPU-staged reference within tolerance — so CI proves the collective executes correctly on real hardware, not just that the code compiles and lints.

## Non-Goals
- Does not change the tensor/pipeline/expert-parallel engines' sharding logic, numerics, or APIs from `2026-06-19-distributed-model-parallel-inference` — only the synchronization primitive underneath `RowParallelLinear` and the topology telemetry feeding `validate_parallel_topology`.
- Does not wire NVML telemetry into the MCP `hardware://` resources (`hardware-capabilities` capability) — this proposal is scoped to the `ai-inference` parallel-execution topology path (`crates/parallel-topology`, `core-host/src/ai_inference/parallel.rs`) only.
- Does not implement cross-node NCCL (multi-node communicator bootstrap/rendezvous); this proposal covers intra-node, single-process multi-GPU NCCL all-reduce only, matching the existing tensor-parallel (intra-node) scope.
- Does not change `cuda-quality`'s runner provisioning (toolchain install, `nvidia-smi`/`nvcc` discovery) — those steps are already verified working; this proposal only adds a test step that exercises the new NCCL code path.

## Impact
- **Affected capability**: `ai-inference` (delta below).
- **Affected code**: `core-host/src/ai_inference/parallel.rs` (`RowParallelLinear::forward`, `discover_cluster_topology`), `core-host/Cargo.toml` (new NVML/NCCL dependency gated behind `candle-cuda`), `.github/workflows/ci.yml` (`cuda-quality` job).
- **Risk**: NCCL communicator setup/teardown on a CI runner with a single physical GPU requires either multi-rank-on-one-device support (NCCL's own loopback/`ncclCommInitAll`) or skipping the multi-GPU assertion when fewer than 2 GPUs are present — the design must specify which, since the verified `cuda-quality` runner currently exposes exactly one GPU (`RTX 3060`). NVML may not be present/loadable on every runner image; the binding must degrade to `free_vram_bytes: 0` rather than failing the build when `nvmlInit` fails at runtime.
