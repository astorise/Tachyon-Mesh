## Context

`core-host`'s HTTP router (`app_runtime::build_app`) has always unconditionally mounted `admin_plane::authenticated_routes(...)` (the full `/admin/*` surface: IAM, manifest/canary/chaos control, node registry, asset uploads, OpenAPI docs) alongside `admin_plane::bootstrap_routes()` (the two unauthenticated enrollment endpoints). CI's feature-matrix jobs (`feature-matrix-tests`, `feature-matrix-artifacts` in `.github/workflows/ci.yml`) build and test `core-host` across five feature combinations and run with `RUSTFLAGS="-D dead_code"`, so any code that becomes unreachable under a given combination fails the build there rather than just warning locally.

## Goals / Non-Goals

**Goals:**
- Let a node be built with no `/admin/*` surface at all, via a Cargo feature, on by default so existing deployments and docs are unaffected.
- Keep the node enrollable in that configuration — zero-touch/PIN bootstrap must still work.
- Keep both feature configurations compiling clean under the CI feature-matrix's `-D dead_code` gate, without hand-tracing every transitive caller.
- Validate the new behavior with a real router-level test, not just a unit test of a handler function.

**Non-Goals:**
- Shipping a pre-built worker release artifact (`get-tachyon.sh`/`.ps1`) or a worker Docker image. Both the release scripts and the Dockerfiles only support additive `CARGO_FEATURES`, never `--no-default-features`; adding that is a separate, riskier change to shared release infrastructure and is left for later.
- Gating the human-operator IAM signup/login routes (`/auth/signup/*`, `/auth/login/*`, `/auth/recovery/consume`). These predate the `admin_plane.rs` extraction (#295), are orthogonal to it, and the issue's own acceptance criteria only calls out `/admin/*` reduction — expanding scope there was judged out of bounds for this change.

## Decisions

**Feature boundary = `admin_plane.rs` + `openapi.rs` as whole modules, not a scattering of route-level flags.** Gating at the module level (`#[cfg(feature = "admin-plane")] mod admin_plane;`) is the smallest, most legible boundary that maps directly onto "no `/admin/*` HTTP surface" — one `mod` declaration and one merge call in `build_app()` are the only structural changes needed to remove the surface. `openapi.rs` is gated alongside it since its only consumer (`admin_openapi_schema_handler`) lives inside `admin_plane.rs`.

**Enrollment bootstrap moved to `integrity_config.rs`, not left inside a partially-gated `admin_plane.rs`.** The alternative — keeping `bootstrap_routes()` in `admin_plane.rs` and only gating `authenticated_routes()` — would mean `mod admin_plane` itself couldn't be `#[cfg]`'d as a whole, defeating the "smallest legible boundary" goal above. Moving the two bootstrap handlers (already forwarding to `system-faas-node-registry`, so they carry no admin-only logic themselves) next to their sibling enrollment types in `integrity_config.rs` keeps `admin_plane.rs` 100% admin-only and unconditionally compilable elsewhere.

**Orphaned code outside `admin_plane.rs` gets `#[cfg_attr(not(feature = "admin-plane"), allow(dead_code))]`, not `#[cfg(feature = "admin-plane")]` removal.** Early in implementation this was assumed to be an all-or-nothing choice; empirically running `RUSTFLAGS="-D dead_code" cargo check -p core-host --no-default-features --features ring` (rather than statically tracing call graphs) surfaced ~40 items across `auth.rs`, `system_storage.rs`, `kv_cache.rs`, `volume_backup.rs`, `mesh_dispatch_metrics.rs`, `scoping/mod.rs`, `memory_governor.rs`, `domain_types.rs`, and a manifest/nodes/bundle cluster inside `integrity_config.rs` that only `admin_plane.rs` called. Several of those (IAM handlers, kv-cache admin handlers) are also exercised directly by unit tests that bypass the router entirely — hard-removing them with `#[cfg(feature = "admin-plane")]` would have broken those tests when the feature is off. `allow(dead_code)` keeps every such item compiled in both configurations; only the HTTP *route* disappears. This trades a small amount of "smaller binary" benefit (these are leaf handlers, not the bulk of the admin surface) for zero risk of an unpredictable dead-code cascade or test breakage. Rustc's dead-code lint does **not** propagate liveness from an `allow`-annotated function to the functions it calls — each item needed its own annotation; this was confirmed by observation, not assumed.

**Worker-profile feature set for CI/README is `ring,rate-limit,resiliency,mtls,secrets-vault,websockets`, mirroring the existing "security" matrix combination plus `ring`.** Investigation of the mesh dispatch path (gossip config-update, `serve_http_listener`, FaaS dispatch) found no Cargo feature gates required for basic operation — the true minimal `--no-default-features` build already works. The richer combination was chosen for the CI/README example because it represents a realistic production worker (TLS, mTLS gateway, rate limiting/resiliency, websocket mesh dispatch) rather than the bare floor, matching the issue's own example syntax (`--features <transport...>`).

**Verification test lives at the router level (`http_router.rs`), not as a new e2e/Docker/k3d pipeline.** The existing `e2e-zero-touch.yml` k3d workflow already deeply covers the OIDC zero-touch cryptographic path, which is entirely inside `system-faas-node-registry`/`system-faas-cert-manager` and unaffected by whether `core-host`'s admin HTTP surface is mounted. Extending that pipeline to build a second, `--no-default-features` Docker image would need Dockerfile changes (today `CARGO_FEATURES` is additive-only) for coverage that a fast, deterministic `build_app()` + `.oneshot()` integration test already provides for the part that actually changed: the router surface. `worker_profile_completes_enrollment_bootstrap_with_no_admin_surface` runs under the real CI worker-profile feature combination and drives real HTTP requests through the real router (enrollment start/poll against the real `system-faas-node-registry` WASM guest), which is this project's established pattern for this class of test (see `enrollment_start_is_reachable_without_admin_auth`).

## Risks / Trade-offs

- **[Risk]** The pre-existing bare `--no-default-features` CI/release combination silently changes meaning (it previously only dropped `ring`; now it also drops `admin-plane`) → **[Mitigation]** Called out explicitly in a comment on that matrix entry in `ci.yml` and in this proposal; a dedicated worker-profile entry with the realistic transport feature set was added alongside it so the "no admin surface" case is exercised with a production-shaped feature set, not just the minimal floor.
- **[Risk]** `allow(dead_code)` keeps admin-only code paths compiled into worker binaries, so the binary-size reduction is smaller than a full removal would achieve → **[Mitigation]** The bulk of the surface (`admin_plane.rs`, `openapi.rs`, including `utoipa`-generated OpenAPI codegen) is fully removed via module-level `cfg`; only small leaf handlers remain compiled-but-unreachable. Acceptable given the primary stated goal is attack-surface reduction (no HTTP endpoint), which is fully achieved.
- **[Risk]** No pre-built worker artifact exists yet, so "try it" requires a source build → **[Mitigation]** Explicitly scoped out and documented (README Path C notes this); a follow-up issue can pick up release-pipeline support if there's operator demand.

## Migration Plan

No migration needed — `admin-plane` is in `default`, so existing binaries, deployments, and Docker images are unaffected. Operators who want the worker profile opt in explicitly at build time. No data formats, wire protocols, or existing config schemas change.
