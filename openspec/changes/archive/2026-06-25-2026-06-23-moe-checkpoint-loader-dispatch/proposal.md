# Proposal: MoE Checkpoint Loader for Expert-Parallel Dispatch

## Why
`2026-06-19-distributed-model-parallel-inference` (8/8 tasks, archived-in-spirit) shipped a real, numerically-verified expert-parallel MoE primitive: `ExpertPlacementPlan` (round-robin expert→device placement), `detect_expert_count` (scans tensor names for the `<prefix>.layers.<layer_idx>.*.experts.<id>.*` Mixtral/Qwen-MoE convention), `ExpertMlp` (one expert's SwiGLU MLP), and `ExpertParallelMlp` (gate-then-route dispatch, proven against a per-token dense reference in `expert_parallel_mlp_matches_per_token_dense_dispatch_reference`) — all in `core-host/src/ai_inference/parallel.rs:835-994`. Both that change's own `tasks.md` (Task 6) and `2026-06-22-wire-model-parallel-runtime-dispatch` explicitly disclosed the same gap and deferred it as a follow-up.

Concretely, today:
- `candle_llm_runtime.rs:644` rejects every expert-parallel deployment outright: `GpuDistribution::ExpertParallelism => Err(CandleLlmError::UnsupportedModel { detail: "expert-parallel execution requires an MoE checkpoint loader, which is not yet implemented: the per-expert `ExpertParallelMlp` primitive exists and is numerically verified, but this runtime does not yet load a full MoE (e.g. Mixtral) checkpoint", .. })`.
- This rejection is in fact the *second* blocker, not the first: `try_load_with_topology`'s parallel-strategy dispatch is reached only after `Self::load_llama_config(alias, root)` (line 596) has already run, and that function (also shared by the dense single-GPU path) hard-rejects any checkpoint whose `config.json` `model_type` is not exactly `"llama"` (`LLAMA_MODEL_TYPE`, line 29; enforced at line 678). A real Mixtral checkpoint declares `model_type: "mixtral"`, so it is rejected by `load_llama_config` before the `GpuDistribution::ExpertParallelism` arm is ever reached. There is currently no config-parsing path in this runtime that accepts a non-Llama, MoE-shaped checkpoint at all.
- `ExpertParallelMlp::load` (line 968) takes `hidden_size`, `intermediate_size`, `num_experts`, a pre-built `ExpertPlacementPlan`, and `devices` — all of which today have no caller computing them from a real checkpoint's config or weight tensors. `num_experts` in particular must come from the checkpoint (e.g. HF's `num_local_experts` field for Mixtral), not be invented by the loader.

The result: a fully-tested, sparse, multi-device MoE routing engine that no deployment can ever reach, because the runtime's checkpoint loader doesn't recognize MoE checkpoints as loadable at all. This change adds the missing loader.

## What Changes
1. **Recognize MoE checkpoints at config-parse time.** Add a parallel config path (or extend `ModelTypeProbe`/`load_llama_config`) that accepts `model_type: "mixtral"` (the convention `detect_expert_count`'s tensor-name scan was already built against) and parses the MoE-specific fields HF Mixtral configs declare — `num_local_experts`, `num_experts_per_tok`, plus the existing `hidden_size`/`intermediate_size`/`num_hidden_layers` shared with the dense Llama config — into a typed `MoeConfig`, instead of routing every checkpoint through the Llama-only `LlamaConfig`/`Config` parse.
2. **Detect dense-vs-MoE per layer at load time.** For each transformer layer, call the existing `detect_expert_count(tensor_names, layer_idx)` against the checkpoint's safetensors tensor names. A layer returning `Some(n)` loads `ExpertParallelMlp` (n experts); a layer returning `None` loads the existing dense `TensorParallelMlp`/`TensorParallelBlock` path unchanged — so a checkpoint that mixes dense and MoE layers (a real pattern in some architectures) loads correctly layer-by-layer rather than assuming uniformity.
3. **Build the `ExpertPlacementPlan` from the deployment's strategy, not just round-robin.** `ExpertPlacementPlan::round_robin(expert_count, device_count)` already exists and remains the default; this change wires the deployment's `hardware_strategy.expert_device_map` (the WIT-defined, already-threaded-into-`IntegrityModelBinding` field per `2026-06-22-wire-model-parallel-runtime-dispatch`) as an optional explicit override, so an operator can pin specific experts to specific devices instead of accepting the default even distribution.
4. **Wire the real load path in `candle_llm_runtime.rs`.** Replace the `GpuDistribution::ExpertParallelism => Err(...)` arm with a real loader: parse the MoE config, build the per-layer mix of `ExpertParallelMlp`/dense blocks, assemble them into a new MoE-capable model type, and serve generation through it — reusing `TensorParallelBlock`'s existing attention/norm/cache machinery for the parts of each layer that are unaffected by MoE (everything except the MLP).
5. **Add a decode-capable MoE model wrapper.** Mirroring `TensorParallelLlama`/`PipelineParallelLlama`'s existing `LoadedModel`/`ParallelModel` integration, add an `ExpertParallelLlama` (or equivalently named) struct that owns the embedding, per-layer mixed dense/MoE blocks, final norm, and LM head, and supports both prefill and KV-cache decode (reusing `TensorParallelCache`/`TensorParallelBlock::forward`'s existing attention+cache machinery; only the per-layer MLP dispatch differs between MoE and dense layers).

## Non-Goals
- **No top-k > 1 routing.** `ExpertParallelMlp::forward` implements top-1 routing only (per its existing doc comment); generalizing to top-k Mixtral-style routing (`num_experts_per_tok > 1`, requiring weighted combination of multiple experts' outputs per token) is explicitly out of scope and tracked as a follow-up once top-1 dispatch is proven end-to-end in production.
- **No changes to `ExpertPlacementPlan`, `detect_expert_count`, `ExpertMlp`, or `ExpertParallelMlp`'s core forward logic** — those primitives are already implemented and numerically verified; this change only adds the caller that constructs and drives them from a real checkpoint.
- **No pipeline-parallel-plus-expert-parallel combination** (MoE layers split across pipeline stages) — this change assumes expert-parallelism is the sole distribution mode for a given deployment, matching how `GpuDistribution` is already a single enum value per deployment today.
- **No changes to the tensor-parallel or pipeline-parallel paths.** The decode-KV-cache gap in pipeline-parallel is the separate `2026-06-23-pipeline-parallel-decode-kv-cache` proposal.

## Impact
- **Affected capability**: `ai-inference` (delta below) — expert-parallel deployments move from "always rejected" to "loads and generates for Mixtral-style MoE checkpoints."
- **Affected code**:
  - `core-host/src/ai_inference/candle_llm_runtime.rs` — new MoE config parsing (parallel to `load_llama_config`), new per-layer dense/MoE detection and mixed-block loading, `GpuDistribution::ExpertParallelism` dispatch arm replaces its rejection with a real load, `LoadedModel`/`ParallelModel` gains an MoE variant.
  - `core-host/src/ai_inference/parallel.rs` — no logic changes expected to the existing primitives; may need a small helper to build an `ExpertPlacementPlan` from `hardware_strategy.expert_device_map` instead of only `round_robin`.
  - Possibly a new `core-host/src/ai_inference/expert_parallel_llama.rs` (mirroring the existing `tensor_parallel_llama.rs`/`pipeline_parallel_llama.rs` module split) housing the new MoE-capable model wrapper.
- **Risk**: this is new control flow at model-load time, gated entirely behind `GpuDistribution::ExpertParallelism` — the existing dense and tensor/pipeline-parallel paths, and their `load_llama_config`/`ModelTypeProbe` gate, are unaffected as long as the new MoE config path is additive (a new branch on `model_type`, not a modification of the existing Llama check). The highest-risk item is correctly handling checkpoints that mix dense and MoE layers, which has no existing test coverage in this codebase; mitigated by per-layer `detect_expert_count` dispatch (point 2) plus new tests covering both a uniform-MoE and a mixed dense/MoE fixture checkpoint.
