- **`hardware_strategy.cuda_graph_decode` now actually runs a real captured/replayed decode, for the first request served against a paged-attention Llama-on-CUDA deployment** (`core-host/src/ai_inference/candle_llm_runtime.rs`, `Cargo.toml`, `.github/workflows/ci.yml`, `docs/ai-inference-candle-llm-runtime.md`, issue #312 step 2). A new `CudaGraphDecodeSession` (gated behind `candle-cuda`) pre-allocates the token/position/decode-slot/block-table/seqlens/logits buffers once per request at their full maximum width, runs one uncaptured warm-up forward pass, captures the steady-state decode step via `candle_core::CudaGraph`, and replays it for every subsequent token — every buffer is updated only via `Tensor::slice_set` (device-to-device, no reallocation), matching `CudaGraph::capture`'s documented contract. `model.forward`'s `index_pos` argument becomes irrelevant once both device-tensor seams are attached (confirmed by re-reading every `index_pos` use site in the fork's attention/cache code), so every captured call passes a fixed placeholder while the real position flows through the persistent buffers instead. Requires `hardware_strategy.paged_attention: true` (the contiguous KV cache's per-step `Tensor::cat` reallocation is fundamentally incompatible with graph replay); every other combination keeps the existing typed rejection. Prefill, LoRA adapters, and speculative decoding are unaffected. **Known limitation, still open**: a *second, independent request against the same already-loaded model* fails with `CUDA_ERROR_INVALID_VALUE` on an unrelated allocation. A first upstream fix attempt ([astorise/candle#17](https://github.com/astorise/candle/issues/17), holding `candle-core`'s internal event-tracking bookkeeping paused for a captured graph's whole lifetime) matched the originally suspected mechanism exactly and passed the fork's own new regression test, but re-testing our actual scenario (a captured multi-layer `Llama::forward`, not the fork test's single elementwise op) on real hardware showed the identical failure, unchanged — reported back and reopened the issue; investigation ongoing. **Do not enable `cuda_graph_decode` for any model expected to serve more than one request** until this resolves — effectively every production deployment today. Verified by 188/188 `ai_inference::` tests (0 regressions) on the default CPU build, `cargo clippy -D warnings -D clippy::unwrap_used`, `RUSTFLAGS=-D dead_code cargo check`, and `cargo fmt --check`; the `candle-cuda`-gated capture/replay code itself could not be compiled or tested on this dev machine at all (no working local CUDA toolchain) and is verified solely by the `cuda-quality` CI lane (five real-hardware iterations: a shape bug, then this still-open multi-request limitation). See `openspec/changes/wire-cuda-graph-decode`.

- **Fixed cross-contamination in the continuous batching scheduler's response routing** (`core-host/src/ai_inference.rs`, issue #312 step 4): `process_batch` collected one input per job sharing a decode batch and forwarded the whole batch to `BackendModel::execute`, but every real-model arm (`Qwen35Moe`, `ModelOptNvfp4`, `TextGeneration`/speculative) only ever decoded the *first* prompt in that batch and returned one combined output; `process_batch` then cloned that single output across every job in the batch. Since `DEFAULT_BATCH_SIZE = 32` makes multi-request batches the default (not an edge case), two concurrent different-prompt requests to the same model alias admitted into the same decode step could silently receive each other's generated text. `BackendModel::execute`/`execute_with_adapter` now return `Result<Vec<Vec<u8>>>` (one output per input, in order); the Candle/Qwen/Vendor backends now loop over each input and decode it independently (reusing the existing, already-correct single-prompt decode path once per request rather than once per batch); `process_batch` routes `outputs[i]` back to `batch[i]`'s own response channel and fails the batch outright if the output count doesn't match the request count, instead of misrouting. The existing `scheduler_batches_concurrent_requests_for_same_alias` test couldn't catch this because it sends the identical prompt from every thread to a mock model with a fixed response — contamination and correctness look identical in that setup. A new test, `scheduler_routes_distinct_concurrent_prompts_to_their_own_response`, drives three distinct prompts through a real Candle Llama fixture concurrently and asserts each caller gets back its own prompt's output; confirmed it fails against the old broadcast behavior and passes against the fix. This is a correctness fix via sequential per-request processing, not fused multi-sequence GPU batching for throughput — that remains a distinct, larger follow-up. Verified by 185/185 `ai_inference::` tests (0 regressions), `cargo clippy -D warnings -D clippy::unwrap_used`, `RUSTFLAGS=-D dead_code cargo check`, and `cargo fmt --check`. See `openspec/changes/fix-continuous-batching-response-routing`.

- **`hardware_strategy.paged_attention` now actually runs, for Llama on CUDA** (`core-host/src/ai_inference/{candle_llm_runtime,paged_kv}.rs`): previously an unconditional typed rejection (issue #312 step 1); now enabled for a Llama checkpoint on a CUDA device (every other architecture/device/build combination is unchanged and still rejects). A new `paged_kv.rs` module owns a `PagedBlockPool` (fixed-size free-list allocator, sizeable from a byte budget) and per-request `SequenceBlockTable`s; `candle_llm_runtime.rs` sizes the pool from real NVML free-VRAM telemetry queried after weight load, allocates one `(key_cache, value_cache)` tensor pair per transformer layer, and attaches `cache.set_paged_kv(..)` for every layer on every forward step via the additive `Cache::set_paged_kv`/`paged_kv` seam `astorise/candle` tag `tachyon-v0.11.0-3` added ([astorise/candle#8](https://github.com/astorise/candle/issues/8)). **Discovered mid-implementation**: `candle-flash-attn`'s kernels only support F16/BF16, never F32 (same constraint every real paged-attention implementation has, e.g. vLLM/TensorRT-LLM) — a paged-attention Llama deployment now loads its weights and KV cache in BF16 instead of the contiguous path's F32, so its output is a real, deterministic decode but not bit-identical to the F32 dense path. **Three real bugs caught by `cuda-quality` on actual GPU hardware, one per re-run, none visible from CPU compilation or unit tests**: (1) the first pool-sizing pass omitted `num_hidden_layers` from the per-block byte cost and sized the pool to whatever fit the *entire* free-VRAM budget instead of just the one sequence in flight, which OOM'd a real GPU for the tiny CI test fixture (computed millions of blocks against gigabytes of nominally free VRAM); fixed by capping the pool at exactly one full-length sequence's worth of blocks and including the layer count, with the sizing arithmetic extracted into a pure, CPU-testable function so this class of bug is now regression-tested without needing GPU hardware. (2) The next run got past sizing but failed inside the forward pass: `candle_flash_attn`'s paged kernel hard-requires `page_block_size % 32 == 0`, which the original block size of 16 violated; fixed by using 32 and adding a compile-time assertion so this exact mistake can't be reintroduced silently (its K/V tile width is fixed at 32 for every head dimension specifically so a tile never straddles two pages). (3) The next run got past that too, then failed because `candle_flash_attn` also requires head size to be a multiple of 8, which the shared tiny test fixture's `head_dim = 4` violated (every other test using that fixture never exercises the flash-attn kernel, so this went unnoticed until now); fixed with a dedicated fixture (`head_dim = 8`) used only by the CUDA-gated paged-attention test, leaving the widely-shared fixture untouched. Speculative-decoding verification falls back to plain generation against a paged-attention target/draft (would otherwise dtype-mismatch); LoRA adapters and prefix caching are unaffected (already/still fully independent code paths). Verified by 184/184 `ai_inference::` tests (0 regressions) on the default CPU build, and the CUDA-gated generation test itself is now confirmed green on real `arc-gpu-runners` hardware (PR #342) after all three fixes. `cuda_graph_decode`, `flashinfer_attention`, and continuous batching remain open per issue #312. See `openspec/changes/wire-paged-attention-decode-path`.

### 🛡️ Security & Supply Chain

- **Keyless Signing:** All Linux/macOS release artifacts are cryptographically signed using GitHub OIDC and Sigstore (`cosign sign-blob`). Rekor transparency-log bundles (`.bundle`) are attached to every release.
- **SBOM Generation:** SPDX 2.3 Software Bill of Materials are generated via `cargo sbom` and attached to releases for vulnerability scanning (Trivy, Grype, etc.).
- **Zero-Build Verification:** The `get-tachyon.sh` and `get-tachyon.ps1` installation scripts now enforce SHA-256 checksum validation before extraction, preventing MITM attacks.
- **XSS Immunity:** The entire UI has been rewritten to use native DOM APIs (`el()` / `frag()` helpers). All `innerHTML` interpolation of user data has been eliminated. A strict Content Security Policy is compatible with the new architecture.

### 🤖 AI Agents & MCP (Claude Desktop / Cursor)

- **Error Taxonomy:** Standardised error codes across all 35 MCP tools: `-32602` (invalid params), `-32001` (cluster unreachable), `-32002` (rate limited with `retry_after_ms`), `-32603` (internal error).
- **E2E Test Coverage:** Full behavioural coverage for all lifecycle (`deploy_function`, `list_functions`, `function_logs`, `delete_function`) and KV (`kv_get`, `kv_put`, `kv_delete`) tools. All 12 tests pass without a live cluster.
